# SneppX Shield - Key Management & Rotation

Signing keys for model artifacts are Ed25519 keys generated by
`sneppx-shield keygen`. This document covers storage, protection and
rotation for interactive use and CI.

## Key roles

- **Signing key (secret)** - signs model artifacts. Never committed, never
  shared; lives in a secrets manager or an operator's `~/.config`.
- **Verification key (public)** - embedded in `.sig` files and distributed
  with `sneppx-shield verify --public-key` for offline checks.

## Generating a keypair

```sh
sneppx-shield keygen --out keys/2026-09
# -> prints public_key / secret_key and stores keypair.json
```

`keygen` writes `public_key` + `seed` (the Ed25519 secret seed). The JSON
file is the keypair; protect it with file permissions (`chmod 600`) or an
encrypted vault.

## Signing

```sh
sneppx-shield sign model.pt --secret-key @keys/2026-09/keypair.json --signer "Buildbot 2026-09"
# -> model.pt.sig (contains algorithm, sha256, public_key, signature, signer)
```

## Verifying

```sh
sneppx-shield verify model.pt                 # uses the .sig pk
sneppx-shield verify model.pt --public-key <hex-or-@file>
```

Both also run under `sneppx-shield audit model dir/` (SBOM + signature
check in one pass) and CI mode `sneppx-shield audit model --ci`.

## Rotation procedure

Rotate at least yearly, immediately after a suspected compromise, or when
your registry's latest key age exceeds 180 days.

1. **Generate the new key** for the next period:
   ```sh
   sneppx-shield keygen --out keys/2026-12
   ```
2. **Promote it**: publish the new `public_key` where consumers check it
   (your `sneppx-forge` registry `keys/` archive, release notes, `KEYS.txt`).
3. **Re-sign release artifacts** with the new key:
   ```sh
   sneppx-shield sign model.pt --secret-key @keys/2026-12/keypair.json
   ```
4. **Deprecate the old key**: keep the previous public key published in a
   `keys/previous/` archive so old artifacts still verify, but stop signing
   with it.
5. **Revoke on compromise**: if a secret leaks, sign nothing else with it
   and document the window in your audit report (`sneppx-audits` uses this
   as evidence). Artifacts signed during the exposure window are suspect.

## Layered defense

- Sign a **digest**, not just the artefact: signatures bind `message_sha256`
  so you can verify large files anywhere without shipping copies.
- Snapshot: keep the SBOM (`sneppx-shield sbom`) alongside each release so
  integrity checks don't depend on a single point of truth.

## CI guidance

- Store the secret key in a secrets manager (`GH Secrets`, Vault, `doppler`)
  and never print it. `_read_key_arg` accepts `@file` only so a key encoded
  in the command line doesn't leak into process listings.
- In CI, verification doesn't need the secret at all:
  ```sh
  sneppx-shield verify model.pt --public-key @<CI-exported-pubkey-file>
  ```
